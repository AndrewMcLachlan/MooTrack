# Agent and installer — design

Captures the signals the derivation engine consumes. Second of three
deliverables, after [the derivation engine](2026-09-13-derivation-engine.md).

## Shape

```
src/MooTrack.Agent/       Windows service, net10.0-windows, LocalSystem
installer/                WiX package producing MooTrack.msi
tests/MooTrack.Agent.Tests/
```

The Win32 layer is confined to `Native.cs` and `DesktopMonitor.cs`. Everything
testable off the target machine — journal, spool, bookmarks — is a plain class
with no interop, and is tested.

## Capture

A message-only window owns every subscription and pumps messages on its own
thread:

| Source | Signal |
|---|---|
| `GUID_CONSOLE_DISPLAY_STATE` | `DisplayOn` / `DisplayOff` (dimmed counts as on) |
| `GUID_SESSION_USER_PRESENT` | `UserPresent` / `UserInactive` |
| `WM_WTSSESSION_CHANGE` | `Lock` / `Unlock` |
| `WM_POWERBROADCAST` | `Suspend` / `Resume` |
| `WM_ENDSESSION` | `Shutdown` |
| Event log 4800/4801, 6005/6006/6008 | corroborating lock, boot and shutdown |

A 60-second `Tick` runs on the host's own loop, independent of the notification
path: if a subscription ever goes quiet without throwing, ticks keep flowing and
the silence becomes visible in the data rather than indistinguishable from
absence.

## Durability

The local journal is the commit point. One append-only NDJSON file per local
day, flushed to disk per line, never rewritten. The POST to the collector is
replication and may fail indefinitely without touching the record.

The spool is bounded. At capacity the oldest entry is shed and counted — the
journal already holds it, so what is lost is a replica, never an observation.

Every callback, the tick loop and the recording path each catch their own
exceptions. A failure to spool, or to read the monotonic clock, must not cost
the observation.

## Event log position

`EventBookmark` has no public serialisation on .NET, so the position is the last
processed `RecordId` per log, written temp-then-rename. A torn bookmark reads as
absent rather than as a valid position, because resuming from a half-written
offset would skip exactly the events written while the agent was down.

With a bookmark, start-up replay covers the downtime. Without one it is a first
run: adopt the log's current position rather than importing the whole retained
history, which would back-fill months and duplicate on every reinstall.

Reading `Security` requires elevation. Running as LocalSystem it is available;
when it is not, the agent logs and continues on the remaining sources.

## Installer

`MooTrack.msi`, built by `installer/MooTrack.Installer.wixproj` against the
`WixToolset.Sdk` NuGet package, so no machine-wide WiX install is needed.

The agent publishes as a single self-contained executable — one file to place,
and no .NET runtime dependency on the target.

- Installs to `Program Files\MooTrack`, data under `ProgramData\MooTrack`.
- Registers the service as LocalSystem, automatic start.
- Creates the `MooTrack` event log source, so the service never has to create it
  on first run.
- Failure actions restart the service three times, 60 s apart, resetting daily.
  These are a property of the service definition that Windows honours; they are
  not a supervisor, and if the service is correct they never fire.

The journal component is marked **permanent**: the MSI contains no `RemoveFile`
table, so uninstalling leaves the record intact. The substantiation data outlives
the software that wrote it.

## Starting reliably

A service that has to be started by hand is a broken service. What that requires:

- **Nothing slow on the start path.** Source start-up runs on the thread pool, so
  a large `Security` log cannot delay the tick loop. Measured: with a source that
  takes four seconds to subscribe, ticks are still journalled on schedule.
- **Host survives a background fault.** `BackgroundServiceExceptionBehavior` is
  `Ignore`; the default stops the host, which would stop the service.
- **One failing source does not take the others down.** Each starts inside its own
  try/catch, and `Security` requiring elevation is handled, not fatal.
- **The composition root is tested.** `AddAgent` is exercised by tests that build a
  real host and resolve the hosted service both with and without a collector
  configured — a DI mistake is the most common reason a service fails to start,
  and it is a compile-clean, run-time-only failure otherwise.

## Configuration

`appsettings.json`, section `MooTrack`; every key overridable by environment
variable as `MooTrack__<Key>`.

| Key | Default |
|---|---|
| `JournalRoot` | `%ProgramData%\MooTrack\journal` |
| `BookmarkPath` | `%ProgramData%\MooTrack\bookmarks.json` |
| `CollectorUrl` | empty — journal only, no spooling |
| `ApiKey` | empty |
| `User` | empty |
| `TickSeconds` | 60 |
| `FlushSeconds` | 300 |
| `SpoolCapacity` | 20000 |

An empty `CollectorUrl` disables the spooler entirely, which is the correct
state until the collector exists.

## Verified

Run against this machine: power notifications delivered to the message-only
window, journal written and read back by the engine, first-run replay bounded,
`Security` denial handled without stopping the agent. The MSI's service entry,
component permanence and absence of removal actions were read back out of the
built package.

## Not doing

A watchdog, a second recorder process, internal watchdog threads, or
subscription liveness probing. A service that needs a watchdog is a service with
a bug; the answer is to fix the bug. Stability comes from a start path that
cannot block, a host that survives faults, and exception handling at every
boundary.
